# ADR-0031: Single Courtyard Scene with Zone-Activated Golden Judgment

- **Status:** Accepted
- **Decision owner:** Architecture
- **Date:** 2026-09-28（v2 amendment 2026-09-29；v3 amendment 2026-09-30；Accepted 2026-09-30 owner 拍板——v1 落地 / v2 分区激活 / v3 展亭模式证据链完整，见 Evidence 末段）

## Context

The showcase catalog grew into 18 flat, ungrouped scenes (`labs/scenario-model/src/catalog.rs`, `labs/scenes/src/registry.rs`): three environment variants sharing one builder, two outline scenes split only by tier, stress/performance as separate near-identical instance loads, and linear prev/next navigation with no grouping. The owner asked for a single scene.

Two constraints shape the decision. First, industry practice for golden-image regression is overwhelmingly "many small isolated scenes, one baseline each" (Unity Graphics Tests, Babylon.js validation tests, three.js/Bevy example screenshots, Skia Gold, Godot proposal #1760); composed gallery scenes exist only as showcase/teaching assets kept separate from the test suites (Unreal Content Examples, Unity Material Samples). No major renderer anchors core regression on a few composed scenes. Second, local verification (2026-09-28) found the naive single-scene data had to be corrected: the 1:1 golden frame crops the pedestal ring at the originally proposed camera (moved to eye z=16), Cel material has no emission so the night lamp field must use Character material (`crates/bevy-stylized-render/src/material.rs:44-55` vs `character.rs:204`), emission is attenuated by fog (lamp depth ≤ 38 m against the night fog end of 40), and the LOD axis must be re-solved against the 10/25/50 band thresholds from the new camera position.

**Owner feedback 2026-09-29 (v2 amendment driver):** after the v1 implementation landed and the interactive window smoke finally ran, the owner rejected the core presentation concept — all zones visible simultaneously in one panorama. The redesign constraint: **the default and judgment paths must never display all content at once**. (The same smoke found three interactive-path defects, fixed same day: window camera missing `Tonemapping::None`, the egui overlay `Camera2d` clearing over the 3D scene, and the missing `PrimaryEguiContext` mount — none affect the capture/golden path.) The v2 amendment keeps the single-scene organization and all verified layout/camera/material data, and changes the presentation semantics to **zone activation**: each view spawns only the focused zone's exhibits on a persistent environment shell. This also aligns the judgment layer with the industry evidence above — per-zone views are the "one subject per frame" form — and structurally removes the noise sources v1 had to manage (background lamp/wall screen-outline flapping, lamps ROI covering the whole panorama width, lamp-fog piercing of far-field judgment).

## Options

1. Keep the 18 isolated scenes; add only grouping metadata. Zero risk, zero consolidation.
2. Converge to 13 scenes / 12 families per the `docs/showcase/01-showcase-examples-fixtures.md` §380-409 table. Partial consolidation; the flat-list problem shrinks but persists.
3. One composed courtyard scene whose panoramas carry whole-frame golden baselines (18 → 8 baselines). Rejected by the evidence above: any rendering change anywhere fails the same panorama baseline, fault isolation collapses, and the industry mitigation is finer granularity, not fewer baselines.
4. One composed courtyard scene for content and navigation, with **ROI-layered judgment**: whole-frame loose assertions (non-black, global statistics) plus per-region strict assertions (per-pixel threshold + fail-ratio), tier/parameter states as multiple approved baselines per capture (Unreal local/global error and Add As Alternative; Chromium Gold multiple approved images).

## Decision

Adopt option 4, amended 2026-09-29 to **zone activation (v2)**. The full scene design (layout, verified coordinates, lighting palettes, camera presets, parameter surface, capture matrix, ROI specification, and the multi-platform functional/interaction layer with its command-set extension and phasing) is [`docs/showcase/05-courtyard-scene-design.md`](../showcase/05-courtyard-scene-design.md); its §0 records the owner decisions (single scene; **zone-activated display — never all zones at once on the default/judgment paths**; mixed sphere/GLB display; day default state; GLB packaged into all lanes).

Concretely:

1. One scene `courtyard` replaces the 18 showcase scenes; all current content maps into zones/parameters (mapping table in the design doc §10). No coverage dimension is deleted.
2. **Presentation is zone-activated (v2):** each view spawns only the focused zone's exhibits on a persistent environment shell (ground/paving/wall/empty pedestals); simultaneous all-zone display exists only as an opt-in `overview` browse mode with no golden responsibility. Camera presets map 1:1 to zones; the v1 panorama preset serves only `overview`.
3. **Golden judgment is per-zone whole-frame strict by default (v2):** one subject per frame — the industry-standard isolation form inside one scene. The ROI-layered machinery (golden.json `regions`, AABB projection, double-gate region diff, frame envelope) remains in the harness and continues to serve dark/noisy captures (night lamp field) and as the recorded fallback if hybrid outline noise reappears. The v1 "panorama loose + ROI strict" layering is retired with the panorama.
4. Tier-gated (hybrid outline) and asset-gated (reference GLB) content stays explicit: hybrid judges only in its Standard-tier capture; the GLB dependency narrows to the `courtyard-stage` capture (absence = that capture BLOCKED, never silent); all other captures no longer depend on the GLB.
5. Baselines follow the design: the v1 baseline set (canonical + macos-metal/android-vulkan overlays) is retired and the v2 12-capture matrix is captured via the explicit GOLDEN_REBASELINE flow (GPU required; absence is BLOCKED, not PASS). Dated acceptance records remain unrewritten history.
6. Scene layout is a contract: layout changes invalidate all ROIs and require explicit recalibration.

## Consequences

Positive: one scene answers the organization complaint; navigation groups by zone instead of an 18-item flat list; **(v2)** judgment views are one-subject-per-frame — the same isolation form as the industry survey's "many small isolated scenes", without giving up the single-scene organization; the v1 noise-management burdens (background screen-outline flapping, lamps ROI covering the full panorama width, lamp fog piercing far-field judgment, ROI pairwise-overlap constraints) disappear structurally; the GLB dependency window (lanes without the asset pipeline had no courtyard coverage at all in v1) narrows to a single capture; per-zone dedicated captures restore the `lighting` explicit key-light comparison to pixel level (v1 had downgraded it to implicit coverage).

Negative: **(v2)** the just-accepted v1 baseline set (canonical 2026-09-29 + overlays 2026-09-28) is retired before it ever guarded a regression — the recapture cost is paid a second time, and browser/android overlays must be re-seeded on their hosts; the capture matrix grows 10 → 12 (ramp/lighting/stage gain dedicated captures, `courtyard-day` retires, dusk/night/stress re-point from panorama to zone cameras); "one render, many judgments" orchestration savings are given back (v1's M4 honesty note already admitted this saved orchestration, not GPU time); interactive navigation gains a mode distinction (zone vs overview) the v1 design did not need. Carried from v1: the composed scene still couples shared view-layer state (time-of-day palettes, fog, exposure) across captures — multi-capture redness still points at the view layer first; old recipe identities tied to retired scene ids stay invalidated (explicit version/catalog gate rejection, no silent reinterpretation).

Adversarial review 2026-09-28 (same-day, pre-implementation) found and the design doc absorbed: three silent coverage cuts (post had no capture; posed flag pose had no capture; the trio dropped the off/on and threshold states present in the old face/hair/metal goldens — fixed by three comparison groups of 7 spheres and captures `courtyard-post` / `courtyard-flags`); the catalog `ParameterKind` lacks an enum kind required by the parameter surface (prerequisite); ROI calibration is automated via projected zone AABBs with pairwise-disjoint assertions instead of manual pixel picking; fault-isolation claims are narrowed honestly to material-local changes (cross-region effects — shadows, fog, global light direction — pierce ROIs by nature); the "one render, many judgments" claim is reframed as saving orchestration, not GPU time; the wire-protocol migration list (suites.json, browser/android lane derivation, catalog-scene.txt) is enumerated. One finding from the adversarial review (S4) was decided by the owner on 2026-09-28: the reference GLB **is** packaged into every lane (browser via HTTP asset source, Android via APK assets) and becomes a required dependency of the courtyard; absence fails the whole build as BLOCKED with no empty-pedestal degradation. Accepted cost: lanes without the asset pipeline ready have no courtyard coverage during the window — an explicit BLOCKED state, not a silent gap. **(v2, 2026-09-29)**: the S4 packaging decision stands; its blast radius narrows to the stage capture per consequence 4 above.
